### What the published numbers already suggest

Reviewers measure 80–100 MB/s sustained sequential write on good UHS-I cards, against a
requirement of 31.75 MB/s. **That is 2.5–3× margin, and it means 90 minutes is likely to
survive.** Two reasons to measure anyway rather than take the win:

1. Those benchmarks run on a PC reader at SDR104, on a card that is not 80% full, over
   transfers that may fit inside the card's SLC cache. All three flatter the number.
2. The requirement is not "a good card is fast." It is "**these exact SKUs**, at 80% full,
   worst-case window." Only a measurement produces that, and only a recorded measurement
   survives a silent controller revision inside the SKU.

### Bus headroom — worth knowing before the measurement comes back

| Rung | Bus ceiling | 90 min (953 MB) | 60 min (635 MB) |
|---|---:|---|---|
| SDR104 | 104 MB/s | comfortable | comfortable |
| SDR50 | 50 MB/s | 63% utilisation — feasible | 42% — comfortable |
| High-speed 4-bit | 25 MB/s | **impossible** (charter already prices this at 43 s) | 25.4 s — passes, barely |

**The useful conclusion: a 60-minute cartridge survives the total loss of UHS-I.** Even the
bottom rung of the sanctioned ladder meets 30 s at 635 MB. A 90-minute cartridge requires at
least SDR50 to work. That is a cleaner statement of the risk than "90 minutes needs the hard
circuit", and it is worth Michael having when he answers Q-002.

### A limitation worth stating before Michael spends the money

**The bench build cannot validate the 30-second copy, and it should not be asked to.** The
Teensy 4.1 has one 4-bit SDIO port (its built-in socket). A second card has to hang off SPI at
roughly 10–20 MB/s, so a bench copy of a 90-minute cartridge would take 60–95 s no matter how
good the cards are. That is a property of the bench platform, not a finding about the design.

So the two jobs split:

- **Card characterisation → a PC with the reader in order 1a.** Faster to set up, cleaner data,
  and available the day the cards arrive rather than after WP-17.
- **Bench build → function, not throughput.** Hot-swap detect, the LED row, the button matrix,
  the interlock, the solenoid one-shot. All of WP-18 and WP-20 except the number.

This should be reflected in WP-18's acceptance criteria, which currently read as though the
bench proves the copy time. Flagged to the PM in `docs/REVIEW/hardware-lead.md`.

## Media atomicity — the second measurement, and the more important one

PM Decisions 004 §1. **The whole format rests on this one unverified physical
assumption:** that a 512-byte SD block write is atomic under power loss. `tapefs` §8's
commit protocol is built on it and every crash-safety guarantee in the project reduces to it.
It is widely believed and **not guaranteed by the SD specification.**

> On each candidate SKU, powered from a switched supply: write a known 512-byte pattern to a
> fixed block, cut power at randomised offsets inside the write window, then re-read. Across
> **≥ 1 000 cuts per SKU**, every read must return **either** the previous content **or** the
> new content in full — never a mixture.

**A single torn block is a blocker and forces a format change, not a firmware workaround.**
No commit sequence survives a card that tears; we need to know before the format freezes
rather than after four cartridges exist.

### The rig — and what it must prove, not just do

Independent review IR-018 found the first version of this procedure could return **PASS having
never cut a card mid-write**. If every cut lands after the write completed, every read is NEW
and the tool was happy. That is a test of nothing, and it is the same failure as a gate that
measures the wrong quantity. The procedure below is rev 2.

| Element | Detail |
|---|---|
| Switched supply | Logic-level MOSFET in the card's 3V3 rail — MOSFETs are already in order 1b |
| **Busy sense** | **DAT0 sampled at the instant of the cut.** This is the qualifying evidence |
| Cut timing | Teensy hardware timer, armed when the write command is issued |
| Sequencing | precondition → write → cut → re-power → re-mount → read back target and four neighbours |
| Analysis | `media_atomicity.py judge`, against a committed plan |

**A trial only counts if the card was provably in its programming phase — and a DAT0-low
sample does not prove that.** In native 4-bit mode DAT0 is a *data line* during the payload, so
it is low whenever the current bit is zero; the protocol's busy indication is a **distinct phase
entered only after the data-response token is accepted**. In SPI mode the indication is on MISO
instead, so the bus mode has to be stated. A rig that samples a pin and calls it busy will happily
count cuts that landed mid-payload.

So a trial qualifies only if the rig can show the whole sequence:

1. the complete single-block payload was transferred,
2. the data-response token was received and accepted,
3. entry into the protocol-defined busy phase was observed, and
4. that indication was still asserted when the rail opened.

Timestamps alone cannot settle it either — a cut write never reports completion, so there is no
end time to compare against. The judge records and checks all four, plus the bus mode and which
line carries the indication.

The judge reports **attempted** and **qualifying** cuts separately, and **the 1 000 threshold
applies to qualifying cuts only.** A run of 5 000 cuts that all landed outside the busy phase is
not 5 000 data points; it is zero.

**Plan a surplus.** Cut offsets deliberately span 0–1.5 × the nominal write time, so misses are
*expected* rather than exceptional. Planned attempts and required qualifying cuts are therefore
separate numbers — 1 500 attempts for 1 000 qualifying is the default. If misses outrun the
surplus, `plan --extend` issues a continuation under the same run id. **Neither number is
editable downward:** the 1 000 minimum lives in the judge, not in the plan file, so no operator
input can lower it.

**Identity is mandatory on every result.** SKU, revision and CID must be present and must match
the committed plan, and each result carries a digest of that plan. The verdict reports the card
it actually measured, never the card the plan claimed.

**Every trial is preconditioned.** Pattern *N−1* is written **without** a cut, then read back and
required to match exactly, before the cut write of *N* is attempted. Power-cut testing cannot
assume the previous iteration completed — if trial *N−1* was itself cut early, the card still
holds *N−2* and a naive classifier would call a perfectly good card corrupt. The old image has to
be *established*, never inferred.

**The plan is committed before the run.** `plan` emits a run id and the trial list; `judge`
matches results against it and rejects duplicates, missing trials, extras, out-of-range
iterations and SKU mismatches. A row count is not a cut count.

**All four neighbour offsets are mandatory, each with its own baseline** (−2, −1, +1, +2).
Missing or malformed neighbour evidence makes a run **invalid**, not passing — the first version
skipped the check silently when the field was absent, which is the worst way for a safety gate to
behave. Per-offset baselines mean neighbours holding legitimately different data are not reported
as damage.

### What this cannot tell you yet

The rig firmware is not written, and the review is right that a PASS cannot support format freeze
until it is reviewable. Specifically it must be shown to issue a **true single-block raw write**
(not a filesystem write that touches metadata), capture transaction timing, remove power cleanly
rather than browning out, and **bypass any cache on re-read** after repower. A card read back
through a stale controller cache would return the new pattern whether or not it reached the
media.

### Cost### Cost

~1 000 cuts × 6 SKUs at roughly 1–2 s per cycle (write, cut, re-power, mount, read) is
**3–7 hours unattended**. It runs overnight on the bench alongside nothing else. SD wear is not
a concern — the FTL remaps — and repeated power cuts mid-write are precisely the stress the
measurement is for.

```
cd hardware/characterisation

# 1. Commit a plan. Identity is mandatory and the run id is collision-resistant.
#    Plan a SURPLUS: the judge requires 1000 QUALIFYING cuts and misses are expected.
./media_atomicity.py plan \
    --sku "SanDisk Extreme" --revision "PRV1.3" --cid "<card CID>" \
    --attempts 1500 --out plan.json

# 2. The rig runs the plan and emits run.jsonl, one line per attempt.

# 3. Judge against the committed plan. The 1000 minimum lives in the judge and
#    cannot be lowered from the plan file or the command line.
./media_atomicity.py judge --plan plan.json --results run.jsonl \
    --json results/atomicity-sandisk-extreme.json

# If misses outrun the surplus, issue an auditable continuation under the same
# run id rather than editing anything:
./media_atomicity.py plan --extend plan.json --attempts 300 --out plan-ext.json
./media_atomicity.py judge --plan plan.json --plan plan-ext.json \
    --results run.jsonl --json results/atomicity-sandisk-extreme.json
```

Exit 0 on PASS, 2 on FAIL, so a whole set runs from a loop.

**A boundary note.** The rig's Teensy sketch is bench instrumentation, not product firmware,
so I have treated it as mine and it belongs in `hardware/characterisation/`. If the PM reads
`firmware/` as covering anything running on a microcontroller, say so and it becomes a handover
to the Software Lead — the tool above is unaffected either way.

| A-3 | Result recorded against the PM's rule: **≥2 SKUs at ≥35 MB/s worst-case → 90 minutes stands; otherwise 60 minutes** | PM Decisions 001 §1 |
| A-4 | The reader is ruled out as the bottleneck — the fastest card is not pinned to the reader's ceiling | Compare the top two cards' worst windows |
| A-5 | Bench parts sufficient to build one Route A carrier and one Route B carrier | WP-04 |

A-4 is the one an eager tester skips. If the two fastest cards report suspiciously similar
numbers, the reader is the instrument limit and the measurement is void.

## How to run it

```
# one card, filled first, result committed

    --sku "MB-MD128SA/AM" --revision "<CID>" --reader "<reader model>" \
    --fill --json hardware/characterisation/results/samsung-pro-plus-128.json
```

Exit status is 0 for PASS and 2 for FAIL, so the whole set can be run from a loop and the
verdicts read off at the end.
